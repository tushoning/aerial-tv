# 性能调研：「没以前流畅」查的是什么（2026-10-30）

接 [PERF-2026-10-28.md](PERF-2026-10-28.md)。起因：#841 等多位用户说「越升级越卡」「1.65 就挺完美」。

## 结论

1. **界面代码没有变慢。** 小米 MFTR0 上把 1.50、1.65、1.67、1.68、1.69、1.70、1.71 编成不同包名的副本并排装，都完全编译、默认设置（每日一图、单排 5 个、底板），交替测两轮：首页移动、进网格、控制中心、长按菜单的中位数在各版本间相差不到 1 ms（14 / 15 / 15 / 14 ms）。「按住方向键连移」所有版本都在 15 ms 和 25–31 ms 之间跳，是测量本身的波动，和版本无关。
2. **真正的原因是用户电视上的 Aerial 没有被编译。** 用户贴的 92 份诊断里有 64 份（约 70%）是 `odex 48 KB` / `profile waiting=true`，也就是只校验、没编译成机器码，只有 1 份是按 profile 编译过的。户主的两台电视每次装完都手动执行 `compile -m speed`，所以感觉不到。
   - **为什么一直编译不了**：控制中心升级、多屏互动推送、U 盘、当贝都走系统安装器。系统安装时只会读和 APK 一起安装的 `.dm` 文件，**不会读 APK 里自带的 `assets/dexopt/baseline.prof`**。APK 自带的 profile 要靠「后台编译任务」，可这个任务要求设备空闲（`deviceIdle=true`）：小米 MFTR0 开机 8 小时，IDLE 一次都没满足过，任务一次也没跑。电视开着时不算空闲，待机时又整机休眠。
   - **为什么「越升级越卡」**：每次升级都会丢掉已编译的代码，现在差不多每天发一版，用户的 Aerial 就一直处于未编译状态。一直停在某个版本不升级的人，可能某天被后台任务编译了，就会觉得「那一版很顺」。这一点是推断，没法直接验证。
   - **影响多大**（同一个 1.71 包，只改编译状态，进程重启后测）：

     | 小米 MFTR0（Android 14，32 位） | 未编译 | 完全编译 | 带 `.dm` 安装 |
     |---|---|---|---|
     | 主线程每帧 | 5–6.5 ms | 3 ms | 3 ms |
     | 首页移动 中位 | 17 ms | 14.7 ms | 14.7 ms |
     | 按住连移 中位 | 31 ms | 14.8 ms | 15–27 ms（波动） |
     | 进网格 中位 | 19–21 ms | 15 ms | 15 ms |
     | 长按菜单 中位 | 18–29 ms | 18–21 ms | 21–23 ms |

     TCL MT5879（Android 11）上的表现不同：未编译时，刚启动后的第一轮有 0.55–0.79 秒的长卡顿（p99 550 / 750 ms），之后 JIT 热起来，中位数和已编译差不多。用户感觉到的就是「卡一下」。
   - 用户报告里慢的电视，GPU 时间都很短：索尼 VH21 中位 25–30 ms，GPU 只有 3 ms；IFFALCON Smart TV Pro 中位 45 ms，GPU 5.5 ms。慢在 CPU，不在 GPU，而且它们都是 32 位 armeabi-v7a、未编译。
3. **`.dm` 修复在小米上已验证**：把 AGP 已经生成的 `baselineProfiles/<n>/*.dm` 加上 `manifest.json`，和 APK 一起安装，系统**在安装时**就按 profile 编译（`status=speed-profile`，`reason=install-dm`），流畅度和手动 `compile -m speed` 一样。有三个坑：
   - **选对文件**：API 31+ 用 `0/`（profile 版本 015），API 28–30 用 `1/`（版本 010），见 `dex-metadata-map.properties`。版本选错时，系统会照样装上，但日志里 `profman` 报 `Profile version mismatch`，结果仍是 `verify`。
   - **加 `manifest.json`**：小米 Android 14 要求 `.dm` 里有 `manifest.json`（`{"packageName":…,"versionCode":…}`），没有就装不上（`INSTALL_FAILED_BAD_DEX_METADATA`）。
   - **Android 8 及以下不支持 `.dm`**，Android 5–6 本来就在安装时全部编译。
4. 另外查过一个「profile 和 dex 校验值对不上」的怀疑，排除了：profile 里记的是 zip 条目的 CRC32，和 APK 一致。`classes2.dex`（desugar 库）不在 profile 里，影响不大。

## 测试环境与方法

- 小米 MiTV-MFTR0：MT9653，4×A73 1.39 GHz，Mali-G52，Android 14，32 位用户空间。TCL MT5879：MT9952，硬件同一档，Android 11。另外，户主的小米显示器 MFFU1 是 MT9655，4×A73 1.8 GHz，Mali-G57，三台里最强，不适合当低端样本。
- 历史版本：把 `applicationId` 改成 `app.orchard.tv.v150` 这类、用 guard flavor（没有 HOME）编译，`adb install` 后和户主的 Aerial 并存，互不影响。测完都已卸载。测量用 `tools/perf.py` 的改版：包名可配，「回首页」改成 `am start` 这个副本。
- 户主的 1.71（户主设置）基线：小米（航拍壁纸）首页移动中位 22 ms，GPU 9.1 ms；进网格 33 ms；控制中心 30 ms。TCL（渐变壁纸）各操作 9–16 ms。
- 诊断报告：用 `gh api` 拉下全部 issue 和评论，解析每份 `### Aerial diagnostics` 的 `Frames` / `Compiled` / `Effects` 行。

## 已实施：应用内升级带 `.dm`（2026-10-30 晚，户主同意）

- **构建**：`app/build.gradle.kts` 的 `DexMetadataAssets` 任务，release 包把 AGP 生成的两份 `.dm` 加上 `manifest.json`，放进 `assets/aerial-dm/28.dm`（Android 9–11）和 `31.dm`（Android 12+），每份约 4 KB。
- **升级**（`update/Updates.kt`）：Android 9 起先走会话安装（以前是 13 起），会话里写入 `aerial.apk` 和新包自带的对应 `.dm`。会话写入失败，或者系统报 `DEX_METADATA` 错，就只带 APK 再开一次会话；会话本身失败，或者没有确认页，就照旧退回系统安装器的 `ACTION_VIEW`（#827 的路径）。Android 12 起加了 `setRequireUserAction(USER_ACTION_NOT_REQUIRED)` 和权限 `UPDATE_PACKAGES_WITHOUT_USER_ACTION`：Aerial 更新自己时不再弹确认页。小米 MFTR0 根本没有会话确认页（`CONFIRM_INSTALL` 找不到 Activity），不这么做就一定退回 `ACTION_VIEW`，`.dm` 也会丢。
- **ADB 测试开关** `--ez update_test_self true`：「下载并安装」改装 Aerial 自己正在用的 APK（重装）。适用于 shell 写不了 `Android/data` 的电视（TCL MT5879）。
- **真机验证**（本地包临时改成 versionCode 89 / 90，测完代码里改回 88）：
  - **小米 MFTR0**（Android 14）：adb 装上 89（`status=verify`），控制中心 →「有新版本」→「下载并安装」，没有弹框，几秒后装好 90，回到首页；`speed-profile / install-dm`，安装来源变成 `app.orchard.tv`，桌面守护仍开，受限设置是 allow。户主设置（航拍壁纸）下首页移动中位 19 ms、进网格 18.5 ms，下午的 1.71 是 22 / 33 ms。从设置按主页键回到 Aerial。
  - **TCL MT5879**（Android 11）：多屏互动推送 90 后，同样从控制中心升级（`update_test_self`）。弹出系统确认页，点「安装」后通过了 TCL 的验证器，`dex2oat` 带上 `--dm-fd`，结果是 `speed-profile / install-dm`（用的是 28.dm）。桌面守护和 TCL 的两个 walleve 无障碍服务都在，屏保仍是 Aerial，自启动仍是 allow；从媒体中心按主页键回到 Aerial。
- **没验证的**：
  - 从官网真正联网下载的那一次升级。两台电视现在是测试版 90，比官网的 1.71（88）新，要等下一版发到官网后，在两台电视上各从控制中心升级一次确认。下载代码这次没改。
  - Android 9–10 真机：没有这类机器。
  - 拒收 `.dm` 后只带 APK 重试这条路：两台电视都收下了 `.dm`，这条路没被走到。
  - 安装来源变成 Aerial 以后，TCL 多屏互动下次推送能不能照常覆盖。
- **注意**：两台电视都装着 versionCode 90，**下一次发版 versionCode 至少要 91**。Lite 只跑在 Android 4.x 上，用不了 `.dm`，不用改。

## 建议（按价值排序）

1. ~~**应用内升级带上 `.dm`**~~（已实施，见上一节）（Android 9+）：
   - 发版时把两份 `.dm`（加好 `manifest.json`）作为 Release 附件上传，或者打包进 APK 的 assets。
   - 升级时在同一个 `PackageInstaller` 会话里写入 `aerial.apk` 和对应 SDK 的 `aerial.dm`。
   - 现在只有 Android 13+ 走会话安装，9–12 走 `ACTION_VIEW`，那条路径带不了 `.dm`。要覆盖 9–12，得让它们也先试会话安装，失败再退回 `ACTION_VIEW`（#827 的退路已经有了）。TCL 的验证器只认系统安装器，会先失败一次再退回，需要在 TCL 上实测。**需要户主决定。**
2. **`install.sh` / `get.sh` 改用 `adb install-multiple apk dm`**。现在装完会 `compile -m speed`，已经够用；加上 `.dm` 后，不跑 `compile` 也能编译好，属于兜底。
3. **少发版、或者控制中心不要天天提示升级**：每次升级都会把编译状态清零，Android 8 及以下、多屏互动、当贝、U 盘安装的电视只能等后台任务，而电视很少等得到。比如有修复时才提示，或者分出稳定版。**需要户主决定。**
4. 诊断报告的 `Compiled` 行在未编译时加一句提示，给有 ADB 的用户附上编译命令（`agent.md` 里已经有）。
5. 上一份报告里的 GPU 方向（流畅模式再减、无障碍语义开销）仍然有效，但从用户数据看，大多数慢电视首先是 CPU 慢，所以优先做第 1 条。

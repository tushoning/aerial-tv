# 性能调研：各操作的卡顿程度与优化（2026-10-28）

## 结论

1. **最大的卡顿来源是航拍动态壁纸上的压暗层**。影片播放时，首页每帧都要在影片上画两层全屏渐变（上下渐暗 + 左侧渐暗）。小米 MFTR0 的 GPU 画这两层每帧约 22 ms，单这一项就超过 16.7 ms 的帧预算。改成开机时烘焙一张 128×72 的小图、每帧拉伸画一次以后，首页左右移动从**中位 81 ms 降到 31 ms，GPU 30 ms 降到 13 ms**，掉帧比例从 58% 降到 22%。影片是 4K 还是 1080p 几乎没有影响（实测 GPU 32.9 对 32.1 ms），压力在渐变本身。
2. **个性化面板下面一直在重画整个首页**。面板是不透明的，可它底下的壁纸、压暗、底板、磁贴和一层全屏 25% 暗幕每帧都在画（过度绘制 4 层以上）。改成面板完全滑入后，首页只画面板上方（留出圆角）：**GPU 每帧 40 → 12 ms，中位 90 → 38 ms**。
3. **屏保**的文字压暗原来也是两层全屏渐变，改成烘焙小图、只画上下两条带（和 Lite 一样）：屏保进入时**中位 104 → 46 ms，GPU 38 → 13 ms**。
4. 「流畅」模式在小米上几乎不省（首页 25 → 22 ms，个性化没变），所以**单靠「自动」更早切到流畅救不了慢电视**。用户报告里慢的电视大多被判成「完整」（2–3.6 GB 内存、4 核），但就算判对了，流畅模式能省的也有限。
5. **静态壁纸（新装默认的每日一图）本来就流畅**：小米上首页移动中位 17 ms、GPU 10 ms，只有个性化面板偏慢（中位 40 ms，GPU 16 ms，这次的第 2 项改动也覆盖了它）。
6. 通过控制中心升级、多屏互动推送装的包，在后台编译之前是**解释执行**（小米上 `status=verify`）：主线程每帧比编译后多约 50%，冷启动多约 100 ms（632–702 对 543–562 ms）。

## 测试环境与方法

- **小米 MiTV-MFTR0**（`ro.board.platform=mt5879`，Android 14，4 核，3.7 GB，1080p 60 Hz）：standard release，`compile -m speed` 之后测。按户主要求临时改成**每排 5 个**；其余都用户主自己的设置：双排、玻璃底板、全部名称、效果「完整」、航拍壁纸（画质自动，实际播 3840×2160）。
- 工具：新加的 `tools/perf.py`。脚本在电视上按遥控器键，然后读 `dumpsys gfxinfo framestats`，每个操作单独统计。指标：
  - 系统汇总的 p50（整 ms）和掉帧数（janky）；
  - 最近 120 帧：vsync 到画完的中位数（med）；主线程（ui）；GPU（交换缓冲后 GPU 还要画多久，Android 9+ 才有）。
  - 60 Hz 下每帧预算是 16.7 ms。电视 GPU 弱，**GPU 这一栏决定能不能跑满帧**。
- 每项改动都和不改的版本在同一台电视上 A/B 对比，必要时交替测两轮。例如「不画压暗 / 烘焙小图」交替两轮：中位 21.7/25.9 和 20.5/25.0 ms，GPU 9.9/12.9 和 9.9/13.0 ms，所以烘焙小图只比完全不画多约 3 ms。
- 模拟器：`aerial26`（Android 8，AOSP 手机系统镜像，**没有 leanback**，就是「国产电视装普通安卓」的情况），2 核、内存 1.5 GB。见下文「低版本、低配置」。

## 小米 MFTR0：各操作优化前后

1.67（已编译）→ 本次改动（已编译），航拍壁纸，双排、每排 5 个、底板、全部名称、完整效果：

| 操作 | 1.67 中位 / GPU（ms） | 优化后 中位 / GPU（ms） | 掉帧（系统统计） |
|---|---|---|---|
| 首页左右移动 | 81 / 30 | **31 / 13** | 58% → 22% |
| 按住方向键连移 | 93 / 28 | **51 / 14** | 69% → 28% |
| 进网格再回来 | 41 / 10 | 32 / 10 | 30% → 14% |
| 控制中心 | 31 / 12 | 23 / 11 | 44% → 26% |
| 个性化（打开、左右、上下） | 90 / 40 | **38 / 12** | 70% → 24% |
| 长按菜单 | 75 / 27 | **41 / 13** | 64% → 22% |
| 屏保进入 | 104 / 38 | **46 / 13** | 83% → 24% |
| 冷启动（am start -W） | 543–562 ms | 501–551 ms | — |

中位数从 vsync 算起，GPU 一慢就会排队，所以中位数会比 GPU 时间长。改完后，首页移动 GPU 13 ms，已经在预算内；中位数还在 25–31 ms，主要是这一帧前后影片解码和合成层占着带宽（不画任何压暗也只有 21 ms，静态壁纸是 17 ms）。

静态壁纸（每日一图，1.67）对照：首页移动 17 / 10、进网格 17 / 8、控制中心 15 / 8、长按菜单 17 / 9、个性化 40 / 16。个性化的改动对静态壁纸同样生效，但**改后没有在静态壁纸下复测**。

### 原因怎么找到的

- `debug.hwui.overdraw` 截图：航拍播放时，整个首页背景是绿色（画了 3 层），底板区域是红色（4 层以上）；个性化面板下面整片红色。
- 逐项去掉再测：去掉底板 GPU 25 ms，再去掉名称 24 ms，改单排 26 ms，都只差一点；影片 4K 和 1080p 一样（33 对 32 ms）；只去掉压暗层是 10 ms。所以 22 ms 全在压暗层。
- 同样的压暗，静态壁纸是在 CPU 上预先烘焙进图片的（`Images.shadeForHome`），只有影片模式是每帧用 GPU 画渐变。

## 低版本、低配置

### 模拟器（Android 8 普通手机系统，2 核，1.5 GB）

- **能正常运行**：没有 leanback 的手机系统也能当桌面（设为默认 HOME 后，HOME 键回 Aerial）。内存小于 1.8 GB，所以「自动」判成低端，用流畅模式，单排 5 个。
- **软件 GPU**（`-gpu swiftshader_indirect`）：1080p 下每帧 GPU 40–100 ms 以上，流畅和完整两档测不出差别，长按菜单每帧 200–300 ms。软件渲染比真电视的 GPU 慢得多，又受 Mac 的负载影响（中途 Mac 的 swap 用到 9/10 GB，模拟器还自己重启过一次），**这些数字不能当成真机表现**。
- **宿主 GPU**（`-gpu host`）：用来只看 CPU。主线程每帧的组合、布局、录制合计 2–4 ms，2 核下 CPU 不是瓶颈。但同一个包两次测的首页中位数是 27 ms 和 52 ms，波动太大，做不了 A/B。
- 没做的：Android 5.0 模拟器（`aerial21`）这次没跑，Mac 内存不够；模拟器上的冷启动时间没测出来（`am start -W` 返回 0）。

## 第二轮（2026-10-29）：建议 1–3

### 1. 逐层找开销

- `ConfigReceiver --es skip_layers picture,shade,plate,clock,pill,tiles,shadow,names`：首页这几层不画，下一帧就生效，不保存，重启 Aerial 或 `--es skip_layers ""` 恢复（`ui/components/DiagLayers.kt`）。配合 `tools/perf.py` 比较关掉每层前后的数字。
- 诊断报告的 `Frames` 行在 Android 12+ 加了 GPU 时间（FrameMetrics `GPU_DURATION`），例如小米：`median 23.5 ms … ; GPU median 12.3 ms, p90 15.1 ms`。GPU 时间接近或超过 16.7 ms 的，是 GPU 慢；总时间长、GPU 不长的，是 CPU 慢。
- 小米 MFTR0 上的结果（航拍壁纸在播，首页左右移动，GPU 中位数）：全部画 13.1 ms；去掉压暗 9.7、去掉底板 9.2、去掉磁贴 10.2、去掉时钟 12.0；名称、阴影、壁纸图几乎不花时间（影片在播时壁纸图本来就不画）；全部去掉 2.7 ms。
- 请慢机型用户配合时，让他们贴开关前后的 `Frames` 行，或者有 ADB 的直接跑 `tools/perf.py <ip>:5555 row`。

### 2. 个性化第一次打开预热

首页空闲 3 秒时，控制中心预热之后隔一帧，再把个性化面板以 1% 不透明度画 3 帧，不拿焦点（`WallpaperSheet` 的 `warm`）。小米，进程重启后第一次打开：前 12 帧合计 **1162 → 881 ms，最慢一帧 316 → 181 ms**，和之后的打开（约 1000 ms，最慢约 145 ms）差不多。预热后按方向键，焦点正常移动（截图确认）。

每次打开前两帧仍有 100–150 ms 花在主线程：面板是整块重新组合的。剖析（见下）显示时间分散在 Compose 组合、测量和无障碍语义上，没有单个热点。

### 3. 长按菜单

原来猜的「每次重做圆角遮罩」不成立：遮罩早就按尺寸缓存了（`baked`）。用 simpleperf 剖析后找到两个真正的原因：

- **底板玻璃在主线程烘焙**：菜单一开影片就停，底板换成停下那一帧的玻璃。这一步原来在绘制时（主线程）做，约 37 ms。影片自己的底板早就在后台烘焙，现在静止底板也改成在后台烘焙（`HomeChrome.Plate`），没烘焙好之前继续显示上一块。
- **菜单每次组合都查磁盘**：`CustomIcons.has` 每次都算 SHA-1、查文件，现在每个 App 只查一次。

小米上最慢一帧：长按菜单 99 → 83–90 ms，进网格 135 → 59 ms，控制中心 146 → 66 ms；p99 分别 200 → 85、129 → 81、150 → 77 ms（这三个操作影片都会停，都会换底板玻璃）。菜单打开时第一帧仍约 100 ms，是菜单本身的组合。

### 剖析时另外发现的两件事（没改）

- **无障碍语义**：Aerial 的桌面守护本身就是无障碍服务，所以 Compose 认为无障碍是开着的，每次界面变化都会计算并发送节点信息。个性化打开时这部分约占主线程 15–18%。关掉它（比如让首页对无障碍不可见）能省下这部分，但小米小爱、TCL AI 这类读界面的服务会看不到 Aerial 的内容，要户主决定。
- **影片停下时的取帧**：MFTR0 的 PixelCopy 读不到视频层，所以影片一停就从 Apple 的 1080p 文件联网取那一帧（`FrameReader`）。菜单打开那 1.5 秒里，Aerial 进程 36% 的 CPU 在 binder 线程上为系统媒体服务读 HTTPS、解 TLS，和界面抢 CPU。这是 MFTR0 这类电视的已知做法，取帧本来就要它；可以考虑在影片播放时预先取好，或者延迟到菜单动画结束后再取。

### 怎么剖析 release 包

release 包不能直接剖析。临时在 `AndroidManifest.xml` 的 `<application>` 里加 `<profileable android:shell="true" />`，编译安装（不要提交），然后：

```
adb shell "(simpleperf record --app app.orchard.tv -e cpu-clock -f 4000 -g --duration 2 -o /data/local/tmp/perf.data &); sleep 0.6; input keyevent 82"
adb shell simpleperf report -i /data/local/tmp/perf.data --sort comm
adb shell simpleperf report -i /data/local/tmp/perf.data --comms app.orchard.tv --sort symbol --children
```

小米上 shell 没有硬件计数器权限，要用 `--app` 加 `-e cpu-clock`。符号被 R8 混淆，用同一次编译的 `app/build/outputs/mapping/standardRelease/mapping.txt` 还原类名和方法名。

## 第三轮（2026-10-29）：影片不再压暗

户主看了对比图后决定：**航拍壁纸（和我的视频壁纸）、航拍屏保都不再压暗**。

- 首页：影片上不画压暗；影片停下后换上的那一帧也不压暗（`Wallpapers` 的 `useLiveFrame` 和开机时的定格图，缓存键加了 `clear`，旧的压暗缓存不会再用）。电视输入画面当壁纸时仍然压暗，因为那个画面没法提前烘焙。静态壁纸（每日一图、照片、内置图）照旧把压暗烘焙在图里。
- 屏保：航拍屏保原来**压暗了两层**：首页的全屏压暗没撤，上面又加了文字压暗。小米上同一时刻截图对比：顶部暗 27%，中间（本来不该压暗的地方）暗 16%，底部暗 55%。现在航拍屏保两层都去掉了，照片屏保仍保留文字压暗。
- 大时钟下面的农历和天气详情原来是 72% 白，现在是全白，只是字重轻一些。
- 影片底板的烟色从 18% 加深到 28% 黑，补上原来压暗在底板下面那部分。
- **长按图标时底板变色**（户主发现）：影片一停（长按菜单、控制中心、进网格），底板原来会从「55% 磨砂 + 45% 透出影片」的半透明样子，换成整块磨砂的静止玻璃，看起来变模糊、变了颜色。现在影片壁纸的底板不管影片动不动都用同一种样子，也不再为它在后台烘焙静止玻璃。
- **长按图标时背景闪一下**：影片一停，没被面板遮住时代码会保留暂停的影片；长按菜单原来被当成「会模糊背景的面板」，0.3 秒后把视频层换成 UI 画的定格图。电视对视频层和 UI 层的画质处理不同，换的时候会闪。现在菜单（不在文件夹里时）也保留暂停的影片。
- **面板打开时推迟联网取帧**：影片因为面板（长按菜单、控制中心、个性化、文件夹）停下时，等 450 ms 面板进完再从网上解码那一帧（`LiveWallpaper` 的 `panel`）。面板打开期间玻璃固定不变，所以晚取看不出来。进网格不推迟，因为网格的磨砂背景要马上用到这一帧（#727）。小米上各开 4 次，前 12 帧合计：长按菜单平均 509 → 440 ms（约快 14%），控制中心 632 → 617 ms（在误差内）。效果比预期小，因为这台是 4 核，解码大多在别的核上；2 核电视上应该更明显，但没测。
- **从 App 回首页后航拍卡一段才播放**：回到首页时影片要重新联网缓冲，同时还在「追帧」：从 Apple 的 1080p 文件解码离开时那一帧，换成定格图。影片要等追帧做完才淡入，所以先看到旧定格图，约 2 秒时跳一下，约 3 秒时影片才淡入。现在回首页时影片从定格图那一刻开始播，淡入时是同一个镜头；离开时的位置等影片播了 5 秒后再在影片底下追帧，下次回来从那里接着播，不会一直重播同一段。小米上回首页到影片动起来：2.7–3.2 s → 1.4–1.7 s。中间试过完全不追帧（0.9–1.3 s），但淡入时前后是两个镜头，看起来不对，没采用。第一次回首页（网络冷启动）曾经要 10 秒，那是缓冲本身慢，这次改动帮不上。
- 性能：同一个包、同样布局下只开关压暗，首页移动 GPU 13.1 → 9.7 ms，中位 26 → 20 ms。屏保进入中位 46 → 24 ms，GPU 13 → 9 ms，因为原来有两层压暗。

## 下一步建议（按价值排序）

1. **请慢机型用户逐层测**：#716 康佳 T963、#630 创维、#817 Smart TV Pro 等用静态壁纸、被判成「完整」的慢电视，请他们用 `skip_layers` 逐层关掉，贴 `Frames` 行（已有 GPU 时间）。
2. **影片停下的取帧让开界面动画**（MFTR0 这类 PixelCopy 读不到的电视）：在影片播放时预先取，或者延迟到菜单、面板动画结束后再取。
3. **无障碍语义的开销**：是否让首页对无障碍服务不可见，需要户主决定（会影响语音助手读界面）。
4. **流畅模式还要更轻**：现在只去掉高光、视差、阴影和面板的离屏层。最弱的电视还可以去掉底板玻璃（改成纯色）、去掉名称阴影，或者把整个首页做成一张图层。
5. **升级后未编译**：应用内升级和多屏互动推送装的包要等后台编译，期间解释执行，慢约 50%。小米 Android 14 安装时不认 APK 里的 profile（HANDOFF 已记），暂时没有好办法，可以在诊断报告的 `Compiled` 行旁边提示用户。
